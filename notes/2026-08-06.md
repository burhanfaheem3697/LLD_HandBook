---

## 📌 TL;DR (30-second recall)

- Stop debugging with `System.out.println()` — it's slow, messy, and needs recompiles.
- Use **breakpoints** to pause execution, **step controls** (`F10`/`F11`/`Shift+F11`) to move through code, **watch expressions** to preview values live, and the **call stack** to see how you got there.
- **Conditional breakpoints** let you skip straight to the interesting case (e.g. `tx > 500.0`).
- **HotSwap** lets you edit code *while paused* — the IDE recompiles the single file and pushes new bytecode to the JVM over JDWP, but it can only replace method *bodies*, not structure.

---

## 🎯 Why This Matters

`println` debugging:
- Pollutes source code with temporary logs
- Forces a recompile every time you want to check something new
- Only shows what you *thought* to print in advance

Interactive debugging fixes all three: pause live, inspect the **entire** object graph, and ask new questions on the fly — no code changes required.

## 🔄 Warm-up Review — Architecture & Maven Recap

A quick refresher on concepts that set up today's lesson:

### 1. Package-by-Feature & Encapsulation
Group related classes into one package and keep internals **package-private (`~`)**. Only expose a small, deliberate public "facade." This hides implementation details from outside consumers.

### 2. Joshua Bloch's Rule *(Effective Java)*
> "Minimize the accessibility of classes and members."

Every `public` class/method is a promise — a contract you can't easily break later. Keep things package-private by default so you're free to refactor without breaking downstream code.

### 3. Maven Dependency Scopes

| Scope | Available At | Typical Use |
|---|---|---|
| `compile` (default) | compile-time, test, **and** runtime | Libraries your app actually needs to run |
| `test` | test execution only | JUnit, AssertJ — excluded from the final JAR |

### 4. Git Release Tagging
```bash
git tag -a v1.0.0 -m "version 1 release"
```
Creates an **annotated tag** pinned to a specific commit — a proper release marker.

### 5. Reading Resources: `File` vs `ClassLoader`

| Approach | Works in a packaged `.jar`? | Why |
|---|---|---|
| `new File("...")` | ❌ No | Files aren't real OS paths once zipped into a JAR |
| `ClassLoader.getResourceAsStream()` | ✅ Yes | JVM reads raw bytes directly out of the JAR/ZIP archive |

## ⌨️ Core Debugger Controls (memorize these)

| Action | Shortcut | What It Does |
|---|---|---|
| ▶️ **Start / Continue** | `F5` | Begin debugging, or resume until next breakpoint |
| ⤵️ **Step Over** | `F10` | Run current line, don't enter called methods |
| 🔽 **Step Into** | `F11` | Jump inside the method being called |
| 🔼 **Step Out** | `Shift + F11` | Finish current method, return to caller |
| 🔁 **Restart** | `Ctrl + Shift + F5` | Restart the debug session |
| ⏹️ **Stop** | `Shift + F5` | End the debug session |

**Quick mnemonic:** *Over* stays level, *Into* goes down, *Out* comes back up.

## ⚙️ Deep Dive — How Hot Code Replace (HotSwap) Actually Works

**The question that sparked this:** *"When I edit code mid-debug session, how does the JVM update without a full restart?"*

### The Pipeline

```
[ Source Code Edit ]
        │
        ▼
1. Incremental Compilation   → IDE silently runs javac on just the saved file
        │
        ▼
2. JDWP Transport            → New .class bytecode sent to the JVM over the
                                Java Debug Wire Protocol (the debug socket)
        │
        ▼
3. Class Redefinition        → JVM swaps the method bodies in memory
        │
        ▼
4. Execution Update          → Future calls to that method run the new code
```

### Key Nuances to Remember

1. **Compilation still happens.** HotSwap isn't magic — the IDE detects the save, runs `javac` behind the scenes, and ships the new bytecode over the existing JDWP debug socket.
2. **Method bodies only.** Standard JVM HotSwap can replace *logic inside a method*. It **cannot**:
   - Add or delete fields
   - Change a method's signature
   - Add/remove methods or classes
3. **The current (paused) frame is stubborn.** If you're paused *inside* a method when you edit it, that specific frame keeps running the **old** bytecode until it returns. To force it to use new code immediately, IDEs offer **"Drop to Frame" / Pop Frame** — this resets the instruction pointer to the top of the method so it re-executes with the fresh bytecode.

## 🧠 Engineering Insights

### Print Debugging vs. Interactive Debugging

| Print Debugging (`println`) | Interactive IDE Debugger |
|---|---|
| Pollutes source code | Zero code modification |
| Requires endless recompiles | Pauses live runtime execution |
| Shows only pre-selected values | Inspects the full heap / object graph |
| Output floods the console | Conditional breakpoints isolate the exact bug |

### Real-World / Open Source Context

In frameworks like **Spring Boot** or **Tomcat**, senior engineers debugging a `403 Forbidden` don't modify framework bytecode. Instead they:

1. Attach an interactive debugger to the running app
2. Set a **conditional breakpoint** on `FilterSecurityInterceptor.doFilter()` matching the specific request URL
3. Inspect the live authentication token on the stack frame at the moment of failure

This is the professional-grade version of exactly what you practiced in Exercise 2.

## ✅ Self-Assessment — Reflection Answers

**1. Step Over (`F10`) vs. Step Into (`F11`)?**
`F10` executes the current line and stays at the same stack depth. `F11` dives into the body of whatever method is being called on that line.

**2. Why use conditional breakpoints?**
They stop you from manually clicking through thousands of iterations — execution only halts when your boolean condition evaluates to `true`.

**3. What does the CALL STACK panel show?**
Every active thread frame: the **top frame** is where execution is currently paused, followed by the chain of callers that led to that point.

**4. What are watch expressions for?**
Evaluating dynamic expressions on demand, using the current stack frame's variable scope — without editing any Java code.

**5. Why is interactive debugging superior overall?**
It gives you live state inspection, on-the-fly expression evaluation, full stack frame traversal, and hot-swapping — all without polluting code or restarting the app.
