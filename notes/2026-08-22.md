## 1. Warm-Up Recall: Defensive Copying

Quick refresher from the prior lesson — this sets up *why* Value Objects need to be airtight.

### 🔓 Collection Encapsulation & Reference Leaks
- **Vulnerability:** Returning an internal `ArrayList` (or any mutable structure) directly from a getter hands external code a live pointer to your internal state.
- **Impact:** Callers can mutate size/contents *without going through your domain methods* — encapsulation is broken.
- **Fix:** Return a **defensive copy** (snapshot) or an **unmodifiable view**.

### 💥 Mutation Exceptions
Calling `.add()`, `.remove()`, or `.clear()` on:
- `List.copyOf(...)`
- `Collections.unmodifiableList(...)`

➡️ Both throw **`java.lang.UnsupportedOperationException`**.

### ⚖️ `Collections.unmodifiableList()` vs. `List.copyOf()`

| Dimension | `Collections.unmodifiableList(list)` | `List.copyOf(list)` |
|---|---|---|
| **Nature** | Read-only **View / Wrapper** | True **Snapshot / Defensive Copy** |
| **Source mutations** | ✅ Propagate — changes to the original list show up here | ❌ Isolated — fully decoupled from the source |
| **Complexity** | Time: O(1), Space: O(1) | Time: O(N), Space: O(N) |
| **Best use case** | Fast read-only view when the source is guaranteed constant/internal | Returning internal state safely via public getters |

> 🧠 **Memory hook:** *"Wrapper watches, copy commits."* A wrapper still watches the original; a copy commits to its own frozen snapshot.

### ⏱️ Defensive Copies Before Validation (TOCTOU)

- Always defensively copy **before** validating invariants inside a constructor.
- **TOCTOU = Time-Of-Check to Time-Of-Use.** In multithreaded code, another thread could mutate the mutable parameter *after* your validation passes but *before* you assign it internally — smuggling invalid data past your checks.

```
Thread A: check(param) → valid ✅
Thread B: mutates param → now invalid ❌
Thread A: this.field = param   // 💀 invalid data now persisted
```

**Correct order:**
```
1. Copy the mutable input
2. Validate the COPY
3. Assign the validated COPY
```

## 2. Domain Invariants

> **Definition:** A core business rule that must remain true for the *entire lifecycle* of a domain object — never just at creation time.

**Two-field invariant examples:**

| Object | Invariant |
|---|---|
| `DateRange` (Value Object) | `startDate.isBefore(endDate)` |
| `BankAccount` (Entity) | `balance + overdraftLimit >= withdrawalAmount` |
| `Invoice` (Entity) | `subtotal + tax == totalAmount` |

## 3. The `EmailAddress` Value Object (Worked Example)

```java
import java.util.Objects;

public final class EmailAddress {

    private final String email;

    public EmailAddress(String email) {
        // Safe check: prevent NPE on string methods
        if (email == null || email.trim().isEmpty() || !email.contains("@")) {
            throw new IllegalArgumentException("Invalid email address format: " + email);
        }
        this.email = email.trim().toLowerCase();
    }

    public String getEmail() {
        return email;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof EmailAddress that)) return false;
        return Objects.equals(email, that.email);
    }

    @Override
    public int hashCode() {
        return Objects.hash(email);
    }

    @Override
    public String toString() {
        return email;
    }
}
```

**What to notice here (this is the "template" for every Value Object you'll write):**
- `final` class → cannot be subclassed to sneak in mutable behavior.
- `private final` field → cannot be reassigned after construction.
- **Validation happens inside the constructor** → an invalid `EmailAddress` literally cannot exist.
- `equals()` / `hashCode()` are overridden based on the **field value**, not object reference → structural equality.
- No setters. Ever.

## 4. Value Objects vs. Entities — The Core Model

```
                       DOMAIN CONCEPTS
                             │
             ┌───────────────┴────────────────┐
             ▼                                 ▼
    ┌──────────────────┐             ┌──────────────────┐
    │  VALUE OBJECTS    │             │     ENTITIES      │
    ├──────────────────┤             ├──────────────────┤
    │ • No Identity     │             │ • Has Unique ID   │
    │ • Immutable State │             │ • Mutable State   │
    │ • Attribute /     │             │ • Identity        │
    │   Value Equality  │             │   Equality        │
    │ • Side-effect-free│             │ • Lifecycle &     │
    │   → new instances │             │   State Transitions│
    └──────────────────┘             └──────────────────┘
```

**One-line gut check:**
> *Do I care WHO/WHICH specific one this is over time → Entity.*
> *Do I only care WHAT its attributes currently are → Value Object.*

## 5. The 4 Pillars of a Value Object

| # | Pillar | What it means |
|---|---|---|
| 1️⃣ | **Descriptive Nature** | It measures, quantifies, or describes something (`Color`, `Money`, `Coordinates`, `Dimensions`) |
| 2️⃣ | **Immutability** | Class is `final`, fields are `private final`, no setters — state never changes after construction |
| 3️⃣ | **Structural / Attribute Equality** | Two instances with equal field values are fully interchangeable — no independent primary key or UUID |
| 4️⃣ | **Side-Effect-Free Pure Operations** | Methods never mutate in place — every "modifying" operation returns a **brand-new instance** |

---

## 6. Why Return New Instances Instead of Mutating?

| Reason | Explanation |
|---|---|
| 🐛 **No aliasing bugs** | Since VOs are shared freely across the system, mutating one in-place would silently corrupt every reference holding it |
| 🔢 **Mathematical accuracy** | `5 + 3 = 8` — adding 3 to 5 *produces* 8, it doesn't redefine what "5" means |
| 🗃️ **Hash-collection safety** | Mutating fields on an object stored in a `HashSet` / used as a `HashMap` key corrupts its `hashCode()` → the element becomes unretrievable ("lost" in the bucket) |
| 🔒 **Zero-lock thread safety** | True immutability = safe to share across threads with **no synchronization needed at all** |

## 7. Decision Matrix: VO vs. Entity

| Decision Factor | 🟦 Value Object | 🟩 Entity |
|---|---|---|
| **Equality basis** | Structural / attribute equality (`.equals()`) | Unique identifier (`entityId`) |
| **State mutability** | Strictly immutable | Mutates through lifecycle state transitions |
| **Database storage** | Inlined / embedded in the parent entity's table | Dedicated table with its own Primary Key |
| **Method behavior** | Returns a new instance (`wallet.add(...)`) | Mutates internal state in place |
| **Examples** | `Money`, `EmailAddress`, `DateRange`, `RGBColor` | `UserAccount`, `Order`, `BankAccount`, `Invoice` |
| **Context matters!** | `Address` on an e-commerce shipping label (just descriptive data) | `Address` in a municipal land-registry cadastral database (has its own tracked identity/history) |

> ⚠️ **Key insight:** The *same concept* (`Address`) can be a VO in one context and an Entity in another. Classification depends on **how your domain uses it**, not on the concept itself.

## 8. Coding Practice

### ❌ Exercise 1 — Primitive Obsession Anti-Pattern

```java
// Anti-pattern: Loose primitives accept invalid values without compile or domain errors
public class PrimitiveObsessionDemo {
    public static void processOrder(String email, double amount) {
        System.out.println("Processing order for: " + email + " Amount: " + amount);
    }

    public static void main(String[] args) {
        processOrder("invalid-email-string", -500.0); // BAD: Invariants broken!
    }
}
```

**Why this is bad:** nothing stops `"invalid-email-string"` or `-500.0` from entering the system. Every method that touches these primitives now needs to *re-validate* them defensively — the rules are scattered everywhere instead of living in one place.

### ✅ Exercise 2 — Pure Value Object (`Money`)

```java
import java.util.Objects;

public final class Money {
    private final double amount;
    private final String currency;

    public Money(double amount, String currency) {
        if (amount < 0.0) {
            throw new IllegalArgumentException("Money amount cannot be negative.");
        }
        if (currency == null || currency.trim().isEmpty()) {
            throw new IllegalArgumentException("Currency must be specified.");
        }
        this.amount = amount;
        this.currency = currency.trim().toUpperCase();
    }

    // Side-effect-free: computes and returns a NEW instance!
    public Money add(Money other) {
        Objects.requireNonNull(other, "Cannot add null Money instance.");
        if (!this.currency.equals(other.currency)) {
            throw new IllegalArgumentException("Currency mismatch: " + this.currency + " vs " + other.currency);
        }
        return new Money(this.amount + other.amount, this.currency);
    }

    public double getAmount() { return amount; }
    public String getCurrency() { return currency; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money money)) return false;
        return Double.compare(money.amount, amount) == 0 && Objects.equals(currency, money.currency);
    }

    @Override
    public int hashCode() {
        return Objects.hash(amount, currency);
    }

    @Override
    public String toString() {
        return String.format("%.2f %s", amount, currency);
    }
}
```

**Trace through `add()`:**
1. Validates the `other` isn't null.
2. Validates currencies match (a *business* invariant, not just a null check!).
3. Returns a **brand-new `Money`** — `this` and `other` are untouched.

## 9. Engineering & JDK Connections

### Eliminating Primitive Obsession
- Raw primitives (`double price`, `String email`) force every layer of the app to repeat defensive checks like `if (amount < 0)`.
- Wrapping rules inside a Value Object's constructor means any method that accepts a `Money` or `EmailAddress` parameter can trust it is **already valid** — no redundant checks needed downstream.

### Real JDK Value Objects
- `java.math.BigDecimal` and `java.time.LocalDate` are the canonical examples baked into the standard library.
- `date.plusDays(5)` and `decimal.add(value)` **never** mutate the original — they always return a freshly computed instance, giving you thread safety and predictability for free.

> 💡 If you've ever been bitten by forgetting to reassign the result of `date.plusDays(5)`, that bug is *proof* `LocalDate` is immutable — the original object genuinely didn't change.

## 10. Daily Reflection Summary (Cheat Sheet)

| # | Takeaway |
|---|---|
| 1 | **VO vs. Entity:** VOs = immutable qualities/quantities compared by attributes, no identity. Entities = continuity via a unique ID across state transitions. |
| 2 | **Primitive Obsession:** Anti-pattern of using raw primitives instead of domain-specific types — scatters validation logic across the codebase. |
| 3 | **Purity in Operations:** `Money.add()` and similar methods never mutate in place — they perform pure computation and return brand-new Value Objects. |
| 4 | **Downstream Simplification:** Validating at construction time makes invalid objects **unrepresentable** — this cleans up all the business logic that consumes them. |
| 5 | **Standard Library Precedent:** `LocalDate` and `BigDecimal` prove this pattern at JDK scale — immutable, thread-safe, always returning fresh instances. |
