## 1. Memory Foundations & Warm-Up Recall

### 🧠 Stack vs. Heap Memory

| Memory Area | What Lives There | Lifecycle |
|---|---|---|
| **Stack** | Primitive variables + reference pointers (addresses) | Popped automatically when scope ends |
| **Heap** | Actual object instances | Cleaned up by **Garbage Collection** once *no stack reference* points to it anymore |

> 💡 **Mental model:** the stack holds "arrows," the heap holds the "boxes" those arrows point to. An object dies (becomes GC-eligible) only when every arrow pointing to it disappears.

### 🪞 Identity vs. State Equality

| Comparison | Method | Meaning |
|---|---|---|
| **Reference Identity** | `==` | Do both variables point to the *same memory address*? |
| **State Value Equality** | `.equals()` | Do two *distinct* objects hold the *same data*? (Requires an explicit override — see [Item 10](#-item-10-obey-the-general-contract-when-overriding-equals)) |

### 🛡️ Constructor Guardrails

- Fields → mark **`private`** to block outside tampering.
- Validate **preconditions inside the constructor**, *before* assigning to fields.
- Goal: an object should never be able to exist in an invalid state, even for a moment.

## 2. Core Concept Clarifications

### 🔧 Method vs. Function

| | Function | Method |
|---|---|---|
| **Binding** | Independent / standalone | Bound to a class or instance |
| **Data Access** | Only explicit parameters | Implicit access to internal state via `this` |
| **Common In** | Procedural / functional languages | Object-oriented languages |

### 🧩 Class vs. Type

| | Class | Type |
|---|---|---|
| **Definition** | Concrete blueprint — memory layout + method bodies | Abstract contract — *what* operations exist, not *how* |
| **Example** | `ArrayList<E>` (implementation) | `List<E>` (interface) |

> 💬 Rule of thumb: **"Program to the Type, implement with the Class."**

## 3. Effective Java Deep Dive (Joshua Bloch)

### 📕 Item 17: Minimize Mutability

**The 5 Rules of Immutability:**

1. ❌ No mutators (no setters)
2. 🔒 Prevent subclassing (`final` class, or `private` constructor + static factory)
3. 🔐 Mark all fields `final`
4. 🙈 Mark all fields `private`
5. 🛟 Defensively copy mutable inputs (constructor) *and* outputs (getters)

**✅ Advantages**
- Inherently thread-safe
- No synchronization needed
- Freely shareable across threads

**⚠️ Disadvantages & the Fix**
- Every small change allocates a *new* object → performance cost (e.g., flipping one bit in a `BigInteger`).
- **Fix:** pair the immutable class with a **mutable companion class** (e.g., `String` ↔ `StringBuilder`).

### 📗 Item 10: Obey the General Contract When Overriding `equals()`

The 5 mathematical requirements:

| # | Property | Rule |
|---|---|---|
| 1 | **Reflexive** | `x.equals(x)` → always `true` |
| 2 | **Symmetric** | `x.equals(y)` ⇔ `y.equals(x)` |
| 3 | **Transitive** | `x.equals(y)` ∧ `y.equals(z)` ⇒ `x.equals(z)` |
| 4 | **Consistent** | Repeated calls return the same result (if state unchanged) |
| 5 | **Non-nullity** | `x.equals(null)` → always `false` |

> 🚨 **Crucial Rule:** Overriding `equals()` **always** requires overriding `hashCode()` too (Item 11). Skip it, and `HashMap`/`HashSet` silently break.

> ⚠️ **Inheritance Pitfall:** You can't extend an instantiable class, add a new *value* field, and still satisfy the `equals()` contract (breaks symmetry/transitivity). **Prefer composition over inheritance.**

## 4. Key Code Implementations

### 🧱 Validated Domain Object — `UserAccount.java`

```java
public class UserAccount {
    private final String username; // final => compile-time immutability
    private boolean active;

    public UserAccount(String username) {
        if (username == null || username.trim().isEmpty()) {
            throw new IllegalArgumentException("Username is required");
        }
        this.username = username;
        this.active = true; // explicit initial state
    }

    public String getUsername() {
        return username;
    }
}
```

**Takeaway:** validation happens *before* any field assignment — the object can never be born invalid.

### 🏦 Identity vs. State Gotcha — `BankAccount.java`

- **Default trap:** if you never override `.equals()`, Java falls back to `Object.equals()` → plain reference identity (`this == obj`). Two accounts with identical balances/numbers will still be "unequal."
- **Correct pattern:**

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;                 // fast-path optimization
    if (o == null || getClass() != o.getClass()) return false;
    BankAccount that = (BankAccount) o;
    return Double.compare(that.balance, balance) == 0 &&
           Objects.equals(accountNumber, that.accountNumber);
}

@Override
public int hashCode() {
    return Objects.hash(accountNumber, balance);
}
```

> 🔑 Note the mirrored structure: `equals()` compares the *same fields* that `hashCode()` hashes — this keeps the contract intact.

## 5. Architectural Insights & Design Patterns

### 🧟 Anemic vs. 💪 Rich Domain Model

| Dimension | Anemic Domain Model *(anti-pattern)* | Rich Domain Model *(best practice)* |
|---|---|---|
| **Structure** | Private fields + public getters/setters, zero logic | Private fields + intent-revealing methods (`deposit()`, `withdraw()`) |
| **State Protection** | Weak — setters expose raw internals | Strong — behavior gatekeeps every mutation |
| **Business Logic** | Leaks into external service classes | Lives inside the domain entity itself |
| **Invariants** | Easily bypassed (e.g., negative balance) | Strictly enforced before any state transition |

> 🎯 **The core diagnostic question:** *"Can a caller put this object into an invalid state?"* If yes → anemic. If no → rich.

### 🏛️ JDK Design Exemplars

- `java.time.LocalDate` and `java.lang.String` are the textbook examples of **functional encapsulation**.
- `LocalDate.plusDays()` doesn't mutate — it **returns a new instance**.
- This makes them naturally safe for **concurrent use** — no locks required.

## 6. Daily Reflection & Core Principles

- 🔒 **Trust Boundaries** — Encapsulation draws a perimeter around an object; the object alone is responsible for keeping itself valid over its lifetime.
- 🏷️ **Naming Convention:**
  - Immutable / functional APIs → prepositions: `plus()`, `with()`
  - Mutable / stateful entities → domain verbs: `deposit()`, `deactivate()`
- 🧪 **Dependency Injection** — Passing dependencies through constructors makes unit testing trivial (swap in mocks/fakes without touching production code).
