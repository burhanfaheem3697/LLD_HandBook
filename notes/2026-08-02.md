## 1. Warm-up Recall — Classpath & Maven

Quick-fire Q&A to reload prerequisite context before the main lesson.

| # | Question | Answer |
|---|----------|--------|
| Q1 | Why does `new File("src/main/resources/...")` fail inside an executable JAR? | `File` needs a real, uncompressed path **on disk**. Inside a JAR, resources live zipped up — so a direct disk path throws `FileNotFoundException`. |
| Q2 | Which `ClassLoader` method reads a resource as a stream? | `getResourceAsStream(String name)` — works whether the app runs from `target/classes` or from inside a `.jar`. |
| Q3 | Where does Maven copy `src/main/resources` files during build? | Straight into `target/classes/`, at the **root** of the runtime classpath. |
| Q4 | `<scope>compile</scope>` vs `<scope>test</scope>` in `pom.xml`? | `compile` = default, available everywhere (build + test + run). `test` = only visible during testing; importing it into `src/main/java` causes a compile error. |
| Q5 | Resource-loading flow (sequence)? | `Main` → `getResourceAsStream()` → `ClassLoader` searches `target/classes` or the `.jar` → returns an `InputStream` → back to `Main`. |

**💡 Memory hook:** *"Resources live in the JAR like clothes in a suitcase — you can't reach in with a `File` path; you need a `ClassLoader` to unzip and hand you a stream."*

### Package-private class syntax reminder
```java
// No 'public' keyword on the class = package-private
class Demo {
    private int temp;

    void printHello() {
        System.out.println("Hello from package-private scope!");
    }
}
```

## 2. The Access Control Matrix

This is **the single most important table** in the lesson — memorize it cold.

| Access Modifier | Enclosing Class | Same Package | Subclass (different package) | World (everywhere) |
|---|:---:|:---:|:---:|:---:|
| `private` | ✅ | ❌ | ❌ | ❌ |
| *(default)* package-private | ✅ | ✅ | ❌ | ❌ |
| `protected` | ✅ | ✅ | ✅ | ❌ |
| `public` | ✅ | ✅ | ✅ | ✅ |

**How to read it:** each row is *cumulative* — every modifier includes everything the row above it can do, plus one more circle of trust.

```
private  ⊂  package-private  ⊂  protected  ⊂  public
 (tightest)                                    (loosest)
```

**💡 Memory hook:** *"Private = just me. Default = my roommates (same package). Protected = family (subclasses too). Public = everyone at the party."*

## 3. Why Package-Private Is the Default

Java's designers (James Gosling & team) picked package-private as the **default (no keyword)** deliberately — it's the "safe middle ground."

| If default were... | Problem |
|---|---|
| `public` | Every class accidentally becomes part of your public API. Refactoring later breaks external code that depends on internals. |
| `private` | Classes in the *same package* constantly need to collaborate — you'd be forced to write explicit modifiers everywhere just to talk to your neighbor. |
| **Package-private (actual default)** | Classes in the same package are automatically "friends" — no boilerplate, no C++-style `friend` declarations needed. |

**💡 Takeaway:** Package-private exists so a package can behave like a **cohesive unit** with private internal wiring, while still choosing what to expose.

## 4. Oracle Docs — Core Rules

### Access level hierarchy (restrictive → open)
$$\text{private} \;\rightarrow\; \text{package-private (default)} \;\rightarrow\; \text{protected} \;\rightarrow\; \text{public}$$

### Encapsulation rule
> Fields should almost always be `private`. Expose state only through public/package-private **getters or methods**, so the class can validate or control changes to it.

### Package namespacing rule
> Use **reverse domain names** (`com.company.project`) as package names. Since domain names are globally unique (registered), this prevents naming collisions between unrelated libraries.

## 5. Hands-on Exercise 1: Package Boundary Violation

**Goal:** prove that a package-private class is genuinely invisible outside its package.

**`com.handbook.internal.InternalHelper`** — no `public` on the class:
```java
package com.handbook.internal;

// No public modifier -> Package-Private!
class InternalHelper {
    String getSecret() {
        return "Secret";
    }
}
```

**`com.handbook.client.ClientApp`** — tries to use it from a different package:
```java
package com.handbook.client;

import com.handbook.internal.InternalHelper; // ❌ COMPILATION ERROR

public class ClientApp {
    public static void main(String[] args) {
        // InternalHelper is not public in com.handbook.internal;
        // cannot be accessed from outside its package
        InternalHelper helper = new InternalHelper();
    }
}
```

**Result:** compiler error — `InternalHelper` simply doesn't exist as far as `ClientApp` is concerned.

> ⚠️ **Side lesson from chat:** Statements like `System.out.println(...)` or `new SomeClass()` must be written **inside a method body** (e.g. `main`), never directly inside the class body — the class body only holds *declarations* (fields, methods, constructors), not free-standing executable statements.

## 6. Hands-on Exercise 2: Facade Pattern

**Goal:** expose one clean `public` entry point while hiding the messy implementation behind package-private classes.

```
com.handbook.security
 ├── SecurityService.java    (PUBLIC FACADE)
 └── PasswordEncryptor.java  (PACKAGE-PRIVATE HELPER)
```

**Hidden helper — `PasswordEncryptor.java`:**
```java
package com.handbook.security;

class PasswordEncryptor { // Package-private
    String encrypt(String raw) {
        return "Encrypted:" + raw;
    }
}
```

**Public facade — `SecurityService.java`:**
```java
package com.handbook.security;

public class SecurityService { // Public interface
    private final PasswordEncryptor encryptor = new PasswordEncryptor();

    public boolean registerUser(String user, String rawPassword) {
        String secret = encryptor.encrypt(rawPassword);
        System.out.println("User " + user + " registered with hash " + secret);
        return true;
    }
}
```

**Why this matters:** any code outside the `com.handbook.security` package can only ever call `registerUser(...)`. It has **no idea** `PasswordEncryptor` exists, so the team is free to change/rename/rewrite the encryption logic later without breaking anyone.

## 7. Engineering Insight & JDK Example

* **Public API sprawl risk:** marking *every* class `public` lets external code depend directly on internal helpers. Change that helper later → you break downstream consumers. This is why over-exposing is a design smell.
* **Packages as micro-subsystems:** treat a package like a mini-module —
  * `public` classes = the **front door** (Facade)
  * package-private classes = the **engine room** (implementation)
* **Real JDK example — `java.util.Collections`:**
  * You call the public static factory: `Collections.unmodifiableList(...)`.
  * But the actual concrete class returned, `Collections$UnmodifiableList`, is **package-private**.
  * You are *forced* to go through the public factory method — you can never `new` that wrapper class directly. This is the Facade pattern in the JDK's own standard library.

## 8. Quick Revision Recap

1. **Restrictiveness order:** `private` → `package-private` → `protected` → `public`.
2. **Package-private scope:** visible only to classes in the *exact same* package — not even subclasses in other packages get access.
3. **Architectural safety:** package-private avoids tight coupling, protects internal state from accidental external mutation, and keeps public APIs clean and stable.
4. **Namespace guarantee:** reverse-domain package names (`com.company.project`) piggyback on globally unique registered domains to avoid collisions.
5. **Facade protection:** a public Facade class validates input and offers a stable API while the real logic stays hidden and free to change.
