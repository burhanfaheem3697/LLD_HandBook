## 1. Warm-up Review & Concepts

### 🔑 Quick Recall Table

| Concept | Key Takeaway |
|---|---|
| **`IllegalArgumentException` vs Custom Checked Exceptions** | Invalid parameters = caller contract violation → use **unchecked** `IllegalArgumentException`. Keeps method signatures clean, avoids forcing `try-catch` on callers. |
| **Given-When-Then Pattern** | **Given** = setup/preconditions/mocks → **When** = action under test → **Then** = assertions/verifications. |
| **`@BeforeEach` State Isolation** | JUnit 5 creates a **fresh test class instance per test method**, running `@BeforeEach` each time → guarantees no state leaks between tests. |
| **`assertEquals` vs `assertAll`** | `assertEquals` fails fast (stops at first failure). `assertAll` runs **all** soft assertions and reports every failure together — better for debugging. |
| **Floating-Point Delta Tolerance** | IEEE 754 causes rounding errors (`0.1 + 0.2 ≠ 0.3`). Use a delta (e.g. `0.001`) so tests check `|expected − actual| ≤ delta`. |

### 💻 Warm-up Command

```bash
# Classic approach
git checkout -b feature/task-validation

# Modern approach (Git 2.23+)
git switch -c feature/task-validation
```

> 💡 **Remember:** `switch` and `restore` were introduced to split the overloaded responsibilities of `checkout` (branch switching vs. file restoration) into clearer, dedicated commands.

## 2. Git Internals & Plumbing Mechanics

### 🧬 Core Object Model

Git is fundamentally a **content-addressable key-value store**. Everything is one of three object types:

```text
[ Commit Object ]
   │
   ├── Metadata (Author, Date, Commit Message)
   ├── Parent Commit Hash(es)
   └── Points to ──> [ Root Tree Object ] (Project Root Directory)
                         │
                         ├── file1.txt ──> [ Blob Object ] (File Contents)
                         └── src/      ──> [ Sub-Tree Object ] (Folder)
                                              │
                                              └── App.java ──> [ Blob Object ]
```

| Object | What it Stores | What it Does NOT Store |
|---|---|---|
| **Blob** | Raw file *contents* only | Filename, path, permissions |
| **Tree** | Directory structure — maps filenames + modes → Blob/Tree hashes | File contents directly |
| **Commit** | Root Tree hash + metadata + parent commit hash(es) | Mutable data (it's an immutable snapshot) |

> 🧠 **Mental model:** A commit is a *pointer chain* — Commit → Tree → Blobs. Nothing is ever edited in place; changes create *new* objects.

---

### ⚙️ Porcelain vs Plumbing Command Map

Every high-level ("porcelain") command has a low-level ("plumbing") equivalent doing the real work:

| Action | Porcelain (Everyday) | Plumbing (Under the Hood) |
|---|---|---|
| Create Blob | *(automatic)* | `git hash-object -w <filename>` |
| Stage File | `git add <file>` | `git update-index --add --cacheinfo 100644 <hash> <filename>` |
| Write Snapshot | *(automatic during commit)* | `git write-tree` |
| Create Commit | `git commit -m "msg"` | `git commit-tree <tree-hash> -p <parent-hash>` |
| Move Branch | `git branch <name>` / `git reset` | `git update-ref refs/heads/<branch> <commit-hash>` |
| Switch Active Branch | `git checkout <branch>` | `git symbolic-ref HEAD refs/heads/<branch>` |

> 📌 **Why this matters:** Understanding plumbing demystifies "magic" porcelain commands and is essential for debugging weird repo states, writing Git tooling, or acing internals-focused interview questions.

### 🔍 Deep Dive: Staging Index vs Working Directory

> **The Puzzle:** Why does `git status` show `brief.txt` as **both** staged *and* unstaged simultaneously?

**Answer:** Git compares **content hashes**, not files as monolithic units.

- **Index (Staging Area)** holds **Version A** of `brief.txt`
- **Working Directory** holds **Version B** (e.g., written via `git cat-file ... > brief.txt`)

**Git's 3-Way Comparison:**

| Comparison | Result | Meaning |
|---|---|---|
| Index **vs** HEAD | `new file: brief.txt` | Version A is queued to be committed |
| Working Dir **vs** Index | `modified: brief.txt` | Version B has edits not yet staged |

> 🎯 **Takeaway:** There are always **three snapshots in play** — HEAD (last commit), Index (staged), Working Directory (on-disk). `git status` is just a diff report across these three.

## 3. Reading & Lecture Summary

### 🎥 MIT Missing Semester — Version Control

- Git models history as a **Directed Acyclic Graph (DAG)** — commits point backward to parents; no cycles.
- **`HEAD`**: symbolic reference → currently checked-out branch (or commit directly).
- **Detached HEAD**: `HEAD` points straight at a commit SHA instead of a branch ref → commits made here aren't attached to any branch and can be lost after switching away (unless tagged/branched).

### 📖 Pro Git — Chapters 1 & 3

**Three Core File States:**

```
Modified  →  Staged  →  Committed
(working dir)  (index)   (.git/objects/)
```

1. **Modified** — changed in working directory, not staged.
2. **Staged** — added to index, queued for next commit.
3. **Committed** — safely stored immutably in `.git/objects/`.

**Merge Mechanics:**

| Merge Type | When it Happens | Result |
|---|---|---|
| **Fast-Forward** | Target branch has no divergent commits — just moves ahead linearly | Branch pointer slides forward, no new commit |
| **3-Way Merge** | Branches have diverged | Git finds the **Common Ancestor**, creates a new merge commit with **two parents** |

## 4. Coding Exercises

### 🧪 Exercise 1 — Atomic Commits & DAG Inspection

```bash
# 1. Workspace setup
mkdir -p scratch/git-demo && cd scratch/git-demo
git init

# 2. First atomic commit — added `id` field
git add VersionedEntity.java
git commit -m "feat(core): add VersionedEntity base class"

# 3. Second atomic commit — added `name` field
git commit -am "feat(core): add name field to VersionedEntity"

# 4. Verify the DAG visually
git log --oneline --graph --decorate
```

> ✅ **Skill practiced:** Keeping each commit scoped to **one logical change** (atomic commits).

### 🧪 Exercise 2 — Branching & Merge Conflict Resolution

```bash
# 1. Create feature branch & commit a change
git checkout -b feature/status
# Added: private String status = "ACTIVE";
git commit -am "feat(core): add active status field"

# 2. Switch back to main & make a conflicting change
git checkout main
# Modified same line: private String status = "PENDING";
git commit -am "feat(core): add pending status field"

# 3. Merge → triggers conflict
git merge feature/status
```

**Conflict as it appears in `VersionedEntity.java`:**

```java
<<<<<<< HEAD
private String status = "PENDING";
=======
private String status = "ACTIVE";
>>>>>>> feature/status
```

**Resolution steps:**

1. Manually resolved to: `private String status = "PENDING_ACTIVE";`
2. Verified it compiles: `javac VersionedEntity.java`
3. Finalized: `git commit -am "fix(core): resolve status field merge conflict"`

> ⚠️ **Common pitfall:** Forgetting to remove the `<<<<<<<`, `=======`, `>>>>>>>` markers before committing — always compile/test after resolving.

## 5. Engineering Insight & OSS Standards

### 🔒 Commits as Immutable Snapshots

- Commit **SHA hashes** are derived from: content + metadata + parent hash(es).
- Changing **even one byte** → completely different SHA → history is effectively **tamper-proof**.

### ⚛️ Why Atomic Commits Matter

- Keeps changes **audit-friendly**.
- Enables precise, isolated **`git bisect`** debugging (binary search through history to find the commit that introduced a bug).
- Makes **isolated reverts** possible without unintended side effects.

### 🏗️ Open Source Standards (JUnit 5 / Spring Framework)

- **Conventional Commits** enforced: `feat:`, `fix:`, `docs:`, `refactor:` — enables automated changelogs & semantic versioning.
- **Rebase + squash before merging PRs** → keeps `main`'s DAG **linear and clean**, avoiding noisy merge-commit clutter.

## 6. 🔁 Quick Recall Cheat Sheet

Use this section for **rapid-fire revision** right before a quiz/interview.

| Prompt | Answer |
|---|---|
| 3 tracked file states? | Modified → Staged → Committed |
| What does a Blob store? | Only raw file content (no name/path/perms) |
| What does a Tree store? | Filenames + modes mapped to Blob/Tree hashes |
| What does a Commit store? | Root Tree hash + metadata + parent hash(es) |
| Where do branches live? | `.git/refs/heads/<branch>` — a file with a 40-char commit hash |
| What is `HEAD`? | Symbolic ref to the current branch (or a commit, if detached) |
| Fast-forward vs 3-way merge? | FF = linear pointer move; 3-way = new commit with 2 parents via common ancestor |
| Plumbing for "create commit"? | `git commit-tree <tree-hash> -p <parent-hash>` |
| Plumbing for "move branch"? | `git update-ref refs/heads/<branch> <commit-hash>` |
| Why atomic commits? | Isolated reverts, clean reviews, `git bisect`-friendly |
| Conflict marker meaning? | `<<<<<<< HEAD` = your branch; `=======` = divider; `>>>>>>> branch` = incoming changes |
| Why is history "tamper-proof"? | SHA is a hash of content+metadata+parents — any change alters the hash |
