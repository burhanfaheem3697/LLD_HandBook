## 1. 🐞 Warm-up Review — Key Debugging Concepts

| Concept | What It Does | Why It Matters |
|---|---|---|
| **Conditional Breakpoint** | Pauses execution only when a boolean expression is `true` | Avoids manually stepping through huge loops/recursion |
| **Field Watchpoint** | Pauses on read/write of a specific field | Finds hidden state mutations in legacy/multi-threaded code |
| **Exception Breakpoint** | Pauses exactly where an exception is thrown | Catches bugs before they're silently swallowed |
| **Watch Expressions** | Lets you evaluate arbitrary expressions on live variables | Inspect state without editing source code |
| **Root Cause Analysis (RCA)** | Finds the *structural* flaw, not just the symptom | Prevents recurring technical debt |

> 💡 **Mental hook:** Breakpoints = *"pause here"*. Watchpoints = *"pause when this changes"*. Exception breakpoints = *"pause when this breaks."*

## 2. 🎬 Code Reading Strategies

### 🔽 Top-Down Reading
- **Start:** Public entry points — REST controllers, `main()`, facade methods
- **Direction:** Drill *down* into internals only as needed
- **Best for:** Understanding business flows, user journeys, "how does a request travel through the system?"

### 🔼 Bottom-Up Reading
- **Start:** Core domain entities, primitives, low-level utility algorithms
- **Direction:** Trace *upward* to see how higher layers orchestrate them
- **Best for:** Security audits, persistence/data-mapping review, performance-critical utility code

> 🧠 **Quick recall trick:** *Top-down = "How is this used?"* · *Bottom-up = "What is this built on?"*

## 3. 🧠 Cognition, Mental Models & Refinement

### A. *The Programmer's Brain* — Dr. Felienne Hermans

Three memory systems interact while reading code:

```
                       ┌─────────────────────────┐
                       │  Long-Term Memory (LTM) │
                       │  (Syntax, Patterns, API)│
                       └────────────┬────────────┘
                                    │
                                    ▼
┌─────────────────────────┐    ┌─────────────────────────┐
│ Short-Term Memory (STM) │───>│     Working Memory      │
│ (Variables, State, ~7s) │    │(Processing Logic/Params)│
└─────────────────────────┘    └─────────────────────────┘
```

**Three types of cognitive overload:**

| Type | Cause | Feels Like |
|---|---|---|
| **Lack of Knowledge** (LTM) | Unfamiliar syntax/API | "I don't recognize this at all" |
| **Lack of Information** (STM) | Can't track variable state across files | "Wait, what does this variable hold again?" |
| **Lack of Processing Power** (Working Memory) | Too much branching/nesting | "I've lost track of the logic" |

**Chunking:**
- STM holds only **~4–7 chunks** at once
- Experts recognize *patterns* (e.g., a Guard Clause, a Builder) as a single chunk instead of reading line-by-line
- This is *why* experienced devs read code faster — not because they're smarter, but because they've pre-compiled patterns into LTM

**Beacons:**
- Meaningful names, domain terms, and comments act as *signposts* that tell your brain which mental schema to load from LTM

> 💡 **Recall hook:** Beacons = "signal flares" guiding your brain to the right mental model.

### B. *Refinement Code Review & Continuous Health* — Martin Fowler

- **Perpetual Code Refinement:** Code review isn't just a PR gate — it happens every time you touch nearby code ("**Boy Scout Rule**": leave code cleaner than you found it)
- **Executable Documentation:** Test suites (`*Test.java`) are the *real* source of truth for behavior — showing valid inputs, expected outputs, and contract boundaries without implementation noise

## 4. 💻 Coding Exercise — JDK `ArrayList` Capacity Growth Audit

Traced using `F12` (Go to Definition):

**Step 1 — Public Facade**

```
add(e) → add(e, elementData, s)
```

**Step 2 — Capacity Check**
If `s == elementData.length` (array is full) → `grow()` is triggered → calls `newCapacity(int minCapacity)`

**Step 3 — Growth Formula**

$$\text{newCapacity} = \text{oldCapacity} + (\text{oldCapacity} \gg 1)$$

- `>> 1` = fast integer division by 2
- **Growth factor: 1.5x (50% increase)** when full

**Step 4 — Memory Allocation**
New array created via `Arrays.copyOf(elementData, newCapacity)`

**Step 5 — Time Complexity**
- A single resize costs `O(N)` (must copy all elements)
- But resizes are infrequent → **amortized `add()` cost = `O(1)`**

> 🎯 **Recall hook:** *"Grow by half, copy the whole — but rarely, so it's still O(1) on average."*

## 5. 💡 Engineering Insight — Architecture Audits at Scale

### Framework for Auditing Large Codebases (500k+ lines)

1. **Locate Public Entry Points** — start at facades/controllers, ignore private utils initially
2. **Read Test Suites First** — they're executable specs
3. **Trace Call Trees** — use Call Hierarchy (`Shift+F12`) to map dependencies
4. **Externalize Working Memory** — sketch box-and-arrow diagrams on paper to offload cognitive strain

### Case Study: Google Guava — `Preconditions.java`

- **Pattern:** Public Facade + Internal Delegation Chain
- **Public layer:** `checkNotNull`, `checkArgument`, `checkElementIndex` — clean, defensive-programming signatures
- **Internal layer:** All delegate formatting to package-private helpers (`lenientFormat`, `badElementIndex`)
- **Takeaway:** Keeps the public API clean while consolidating shared logic (string formatting) internally

## 6. 💬 Chat Discussion — End-of-Day Q&A Recap

**Q1. Top-Down vs. Bottom-Up?**
Top-down starts at public interfaces and digs into private internals; bottom-up starts at domain primitives/utilities and moves up toward callers.

**Q2. Why read unit tests as entry points?**
They show real execution contracts — valid inputs, edge cases, expected exceptions — without wading through implementation boilerplate.

**Q3. Why do IDE shortcuts matter over manual navigation?**
`F12`, `Shift+F12`, `Alt+←` give instant cross-file/package traversal, preserving focus and position context.

**Q4. How does `ArrayList` grow?**
Via `oldCapacity + (oldCapacity >> 1)` — a ~50% bump when full, giving amortized `O(1)` inserts.

**Q5. Why do large, un-nested classes hurt comprehension?**
They overload **Working Memory** — too many unstructured variables/branches/state changes to hold at once, with no modular boundaries to "chunk" into manageable units.
