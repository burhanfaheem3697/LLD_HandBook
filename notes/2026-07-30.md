## 🔥 Warm-up Recall & Quick Reference

### 1. Lightweight vs. Annotated Git Tags

| Type | Description |
|---|---|
| **Lightweight Tag** | A simple, static pointer to a specific commit hash. Doesn't move as new commits are added. |
| **Annotated Tag** | A full Git object stored in `.git/objects/`. Carries metadata: tagger name, email, date, GPG signature, and tag message. |

### 2. Semantic Versioning (`v2.4.1`)

```
v  2  .  4  .  1
   │     │     └── PATCH → backward-compatible bug fixes
   │     └──────── MINOR → backward-compatible features
   └────────────── MAJOR → breaking / incompatible changes
```

### 3. Recovering Detached HEAD Work

**Still on the detached commit?** Attach a branch immediately:
```bash
git switch -c feature/rescued-work
# or
git checkout -b feature/rescued-work
```

**Already moved away?**
1. Run `git reflog` to find the "lost" commit hash.
2. Reattach it: `git branch recovery <commit-sha>`

### 4. CI/CD Tag Pushes & Interactive Rebasing

- **CI/CD Automation** — Pushing a tag (e.g. `v1.0.0`) triggers production pipelines: compile → package → build Docker image → deploy to registry.
- **Interactive Rebase** (`git rebase -i`) — Lets you `squash`, `edit`, `drop`, or reword commits for a clean history before merging into `main`.

## 🏗️ Maven Standard Directory Layout

> **Core Idea:** Maven follows **"Convention over Configuration."** Stick to the standard paths, and Maven auto-discovers everything — no manual XML wiring needed.

```text
my-project/
├── pom.xml                     ← Project Object Model (the blueprint)
└── src/
    ├── main/
    │   ├── java/                ← Production source code
    │   └── resources/           ← Production config (properties, XML, YAML)
    └── test/
        ├── java/                ← Test source code (unit + integration)
        └── resources/           ← Test-only config files
└── target/                      ← Compiled classes + final JAR/WAR (auto-generated)
```

> ⚠️ **Common Trap:** Package folders (`com.example.demo`) live **inside** `src/main/java/` or `src/test/java/`. The "source root" convention stops exactly at `java/` — don't confuse the package path with the root.

## ⚙️ Core Maven Architecture & Concepts

### 1. Orchestration vs. Compilation

> 🚫 **Maven is NOT a compiler.**
> ✅ Maven is a **build automation / orchestration engine** — it *delegates* actual compiling to the JDK's `javac`.

### 2. Project Object Model (`pom.xml`) & GAV Coordinates

GAV = the unique "address" of any artifact in the Maven universe:

| Coordinate | Meaning | Example |
|---|---|---|
| `groupId` | Organization / package root | `com.handbook`, `org.springframework.boot` |
| `artifactId` | The specific module/project name | `maven-demo` |
| `version` | Release or snapshot iteration | `1.0.0-SNAPSHOT` |

### 3. The 3 Fundamental Classpaths

Maven isolates dependencies across **three** separate runtime environments:

```
Compile Classpath  │  Test Classpath  │  Runtime Classpath
```

| Scope | Compile (`src/main`)? | Test (`src/test`)? | Packaged for Prod? | Typical Use Case |
|---|:---:|:---:|:---:|---|
| **`compile`** *(default)* | ✅ | ✅ | ✅ | Core libraries (Jackson, Apache Commons) |
| **`test`** | ❌ | ✅ | ❌ | Test frameworks (JUnit 5, Mockito) |
| **`provided`** | ✅ | ✅ | ❌ | Environment-supplied tools (Lombok, Servlet API) |
| **`runtime`** | ❌ | ✅ | ✅ | Implementation drivers (PostgreSQL/MySQL JDBC) |

**Memory trick:**
- `test` = only visible in the test world.
- `provided` = visible everywhere *except* the final package (someone else provides it in prod).
- `runtime` = invisible while coding, but shows up when running/packaged.

### 4. Build Lifecycle Execution Flow

Maven phases run **sequentially** — triggering a later phase auto-runs everything before it:

```
validate → compile → test → package → verify → install → deploy
```

| Command | What It Does |
|---|---|
| `mvn clean` | Deletes the `target/` output folder |
| `mvn compile` | Compiles production code in `src/main/java` |
| `mvn test` | Compiles test classes + runs unit tests (Surefire plugin) |
| `mvn package` | Bundles compiled code into a JAR/WAR inside `target/` |
| `mvn verify` | Runs QA checks — coverage (JaCoCo), integration tests (Failsafe) — before install |

## 🛠️ Practical Exercises & Debugging Case Studies

### Exercise 1 & 2 — Maven Skeleton & Scope Isolation Verification

1. Built a manual project skeleton with a `pom.xml` that scopes `junit-jupiter-api` as `<scope>test</scope>`.
2. Tried importing `org.junit.jupiter.api.Test` inside **production** code (`src/main/java/com/handbook/demo/App.java`) to test whether scope isolation actually holds.

### 💡 Breakthrough IDE Insight: VS Code vs. Maven Terminal

| Stage | Detail |
|---|---|
| **The Problem** | VS Code let JUnit be imported into `App.java` (production code) with *no error shown*, even though JUnit was scoped to `test`. |
| **Root Cause** | IDEs run their own background compiler (VS Code → Red Hat Java Language Server / Eclipse JDT). It indexes dependencies globally into a workspace cache, ignoring Maven's strict phase boundaries. |
| **The Fix** | 1️⃣ Run `mvn clean compile` in the terminal → Maven correctly **fails the build** with `package org.junit.jupiter.api does not exist`. <br> 2️⃣ In VS Code, run **`Java: Clean Java Language Server Workspace`** to purge the stale cache and force re-indexing strictly from `pom.xml` scopes. |

> 🧠 **Takeaway:** Never trust the IDE's "no red squiggles" as proof your build is correct — always confirm with the actual Maven terminal build.

## 💡 Engineering Insight & Open Source Connections

1. **Convention over Configuration**
   Standardized structure means any developer worldwide can clone a Java project and build it instantly — zero custom setup required.

2. **Transitive Dependency Resolution**
   ```
   App → depends on → Library A → depends on → Library B
   ```
   Maven automatically pulls in Library B and resolves version conflicts using **"nearest definition"** rules (the version closest to your project in the dependency tree wins).

3. **Multi-Module Parent POMs**
   Frameworks like Spring Boot use a parent `pom.xml` with `<dependencyManagement>` blocks to lock compatible versions across all sub-modules (e.g. `spring-boot-starter-web`, `spring-boot-starter-test`) — preventing version-mismatch bugs.

## ❓ Critical Revision Questions

<details>
<summary><b>1. Why doesn't <code>mvn package</code> create a single executable JAR with all dependencies bundled in?</b></summary>

Default Maven JAR plugins only bundle your project's own `.class` files and resources. To create an "uber/fat JAR" with all dependencies included, you need a dedicated plugin like `maven-shade-plugin` or `spring-boot-maven-plugin`.
</details>

<details>
<summary><b>2. How does <code>provided</code> scope differ from <code>compile</code> scope?</b></summary>

Both let you compile production code (`src/main/java`) against the dependency. The difference: `provided` dependencies are **excluded** from the final packaged artifact, because the deployment environment is expected to supply them itself (e.g., a Servlet API supplied by the app server).
</details>

<details>
<summary><b>3. What's the key difference between Java's <code>assert</code> keyword and JUnit assertions?</b></summary>

Java's built-in `assert` needs the JVM flag `-ea` (`-enableassertions`) to run at all — without it, assertions are silently skipped. JUnit assertions, by contrast, **always execute** during test runs regardless of JVM flags.
</details>

## 🧾 One-Page Cheat Sheet

```
STRUCTURE            pom.xml, src/main/java, src/main/resources,
                      src/test/java, src/test/resources, target/

GAV                   groupId : artifactId : version

SCOPES                compile  → main + test + packaged   (default)
                      test     → test only
                      provided → main + test, NOT packaged
                      runtime  → NOT main, test + packaged

LIFECYCLE             validate → compile → test → package → verify → install → deploy

KEY COMMANDS           mvn clean      → wipe target/
                       mvn compile    → compile src/main
                       mvn test       → compile+run tests
                       mvn package    → build JAR/WAR
                       mvn verify     → QA + integration tests

FAT JAR                needs maven-shade-plugin / spring-boot-maven-plugin

REMEMBER                Maven ≠ compiler → it delegates to javac
                        IDE cache ≠ Maven truth → trust the terminal build
```
