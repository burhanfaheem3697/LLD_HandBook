## 2. 🧭 Core Concept: What Is a Domain Invariant?

A **Domain Invariant** is a business rule that must remain `true` for the **entire lifetime** of an object — not just at creation.

| Domain | Invariant Example |
|--------|--------------------|
| 💰 Financial | `Account.balance >= -overdraftLimit` |
| ⏱️ Temporal | `Period.start <= Period.end` |
| 📦 Inventory | `Order.items.size() > 0` |

**Key insight:** An invariant is only as strong as your weakest access point. If a caller can reach into your object and mutate a field directly (via a leaked reference), the invariant is *not actually enforced* — it's just a suggestion.

---

## 3. 🔑 The Golden Rule: Copy First, Validate Second

This is the single most important sequencing rule in this entire topic:

```
STEP 1: Defensive Copy  →  STEP 2: Validate the Copy  →  STEP 3: Store the Copy
```

**Why this exact order?**

- If you validate the *original* parameter and copy *afterward*, a concurrent thread can mutate the original **between** the check and the copy.
- This is a **TOCTOU (Time-Of-Check to Time-Of-Use)** race condition — see [Section 8](#8--toctou-race-condition--deep-dive) for the full trace.
- Copying first "freezes" a private snapshot that no external thread can touch, so validation against that snapshot is trustworthy.

> ⚠️ **Common mistake to avoid:** `if (start.before(end)) { this.start = new Date(start); }` — this validates the *original*, not the copy. Wrong order!

## 4. 🧱 Worked Example: `DateRange` Constructor

This canonical example encodes every rule from Section 3.

```java
import java.util.Date;

public class DateRange {
    private final Date start;
    private final Date end;

    public DateRange(Date start, Date end) {
        // 1. Guard against null references
        if (start == null || end == null) {
            throw new IllegalArgumentException("Start and end dates cannot be null.");
        }

        // 2. DEFENSIVE COPY FIRST: Freeze internal state immediately!
        this.start = new Date(start.getTime());
        this.end = new Date(end.getTime());

        // 3. VALIDATE SECOND: Check invariants on internal copies
        if (!this.start.before(this.end)) {
            throw new IllegalArgumentException("Start date must be strictly before end date.");
        }
    }

    public Date getStart() {
        return new Date(start.getTime()); // Defensive copy on access
    }

    public Date getEnd() {
        return new Date(end.getTime());   // Defensive copy on access
    }
}
```

**Annotate this in your head every time you see it:**

| Line | Purpose |
|------|---------|
| Null check | Fail fast before doing any work |
| `this.start = new Date(start.getTime())` | Copy **first** — severs the reference from caller's original object |
| `if (!this.start.before(this.end))` | Validate the **copy**, not the parameter — immune to TOCTOU |
| `getStart()` returns `new Date(...)` | Getter also copies — prevents callers from mutating internal state via the returned reference |

## 5. 📘 Effective Java — Item 50: Defensive Copies

Core rules to remember:

- **Constructor & Getter Isolation** — Always copy mutable inputs (`Date`, arrays, collections) before storing them, and return fresh copies from getters. This prevents **reference leaks**.
- **Order of Execution** — Copy first, validate second (TOCTOU protection — see Section 3 & 8).
- **The `clone()` Subclassing Trap** — Don't use `clone()` for defensive copying when the parameter type could be subclassed by untrusted code. A malicious subclass could override `clone()` to secretly stash `this` in a static list while still returning what looks like a valid copy.
- **Performance & Ownership Transfers** — Defensive copying has a cost. If performance matters and caller/callee **explicitly trust each other**, you may skip it — but you must *document* that ownership is being transferred and the caller must not mutate the object afterward.
- **Modern Immutability Alternative** — Prefer `java.time.Instant`, `LocalDate`, or `List.copyOf()`. Immutable types make defensive copying unnecessary in the first place.

> 💡 **Memory hook:** *"Don't trust the type, trust the copy."* Even `clone()` can lie if the class isn't `final`.

## 6. 📗 Effective Java — Item 15: Minimize Accessibility

- **Information Hiding** — Restrict public APIs so internals can be refactored, tested, and optimized independently without breaking external callers.
- **Default Privilege Level** — Keep members `package-private` by default. Promote to `public` only when it's genuinely part of the intended API.
- **Liskov Substitution Principle (LSP)** — A subclass **cannot** reduce the access level of an overridden method (`protected` → `private` is illegal).
- **Public Fields Risk** — Public mutable fields surrender all control over invariant enforcement and thread safety.

### 🚨 The `public static final` Array Trap

```java
// DANGEROUS: The array reference is final, but elements remain mutable!
public static final String[] VALUES = { "A", "B", "C" };
```

`final` only locks the **reference** — anyone can still do `VALUES[0] = "HACKED";`

**Two fixes:**

| Option | Fix |
|--------|-----|
| **A** | Make the array `private`, expose an unmodifiable list via `List.of(PRIVATE_VALUES)` |
| **B** | Make the array `private`, return a defensive clone: `PRIVATE_VALUES.clone()` |

## 7. ⚔️ Reference Leaks: Attack & Defense

### Visual Model

```
[ Unsafe Design ]
Caller Reference ──────> [ Internal State: Date ] <────── External Mutation (Invariant Broken!)

[ Secure Design ]
Caller Reference ──( Copy )──> [ Internal State: Date ] <── (Isolated from Caller Modifications)
```

### The Attack (`ReferenceLeakDemo.java`)

Passing a mutable object directly into a constructor — or returning it directly from a getter — hands the caller a **live pointer** to your private state.

```java
period.getStart().setTime(someNewValue); // corrupts internal state — no setter ever called!
```

This is dangerous precisely because it bypasses every validation method you wrote. The object's `private` fields were never technically violated by "outside code," yet the invariant is broken.

### The Defense (`SecurePeriod.java`)

Store and return **new** `Date` allocations at every boundary crossing (constructor input, getter output). This severs the caller's reference from your internal one, so mutating what they hold has zero effect on you.

> 💡 **Memory hook:** *"Private" keeps names invisible, not values immutable.* A `private` field holding a mutable object is only as safe as the copies guarding its entry and exit points.

## 8. 🕰️ TOCTOU Race Condition — Deep Dive

**TOCTOU = Time-Of-Check to Time-Of-Use.** It happens when there's a gap between validating a condition and acting on it — and something changes in that gap.

### Trace: What Goes Wrong When You Validate *Before* Copying

```
Thread 1 (Constructor Execution)                 Thread 2 (External Code)
--------------------------------                 ------------------------
1. Checks start.before(end) -> TRUE
                                                  2. Mutates shared 'start' parameter!
3. Executes: this.start = new Date(start)
   (Copies corrupted time value!)
```

Thread 1 validated a value that was true *at that instant* — but by the time it actually copies the data, Thread 2 has already changed it. The invariant check is now stale and meaningless.

> **The Rule:** Always copy inputs *first* into private fields, then validate the private fields. Once copied, external threads have no path to touch your internal state during validation.

## 9. 🌱 Modern Java Alternatives

The best defense against reference leaks is often to **not have mutable state at all**.

- **`java.time` API** (`Instant`, `LocalDate`, `ZonedDateTime`) — value-based and immutable by design.
- Methods like `.plusDays()` or `.withHour()` return **entirely new instances** rather than mutating the original.
- Result: defensive copying becomes unnecessary, because there's nothing to leak — every instance is inherently safe to share.

> 💡 **Rule of thumb:** If you're reaching for defensive copies constantly, ask whether an immutable type could eliminate the problem at its root.

## 10. 🔍 Unmodifiable Wrapper vs. True Copy

A subtle but frequently-tested distinction:

| Method | Behavior | Reflects Source Changes? |
|--------|----------|----------------------------|
| `Collections.unmodifiableList(list)` | Creates a read-only **wrapper** around the original list | ✅ Yes — if source list changes, wrapper reflects it |
| `List.copyOf(collection)` | Creates a true **immutable snapshot** | ❌ No — completely isolated from the source |

> ⚠️ **Trap to remember:** `unmodifiableList` prevents *you* from modifying it through that reference, but it does **not** protect against the *original* list being modified elsewhere. Only `List.copyOf()` gives a true, independent defensive copy.

---

## 11. 🧠 Key Reflections & Takeaways

1. **Reference Leak Mechanism** — Exposing mutable internal references lets callers bypass validation methods entirely and corrupt private fields directly.
2. **Copy Order Necessity** — Copying before checking protects against concurrent modification (TOCTOU) attacks during object construction.
3. **Immutability Advantage** — Immutable classes eliminate defensive-copying boilerplate, reduce allocation overhead, and guarantee thread safety by design.
4. **Encapsulation ≠ `private`** — `private` is just a compiler-enforced visibility rule. **True encapsulation** is the architectural discipline of guarding invariants and forcing all state transitions through valid, behavioral methods.
