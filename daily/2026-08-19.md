# Today's Objective

* **Today's Focus**: Deep dive into **Encapsulation**, **Domain Invariants** (rules that must hold true throughout an object's lifecycle), **Access Control**, and **Defensive Copying** (preventing reference leaks of mutable arguments like `java.util.Date`, arrays, or `List`).
* **Why Today's Work Matters**: Making fields `private` is not enough to achieve true encapsulation. If a getter returns a reference to a mutable object (e.g., `public Date getStartDate()`), external code can mutate your object's internal state directly, bypassing all validation logic and breaking domain invariants.
* **How it Connects to Previous Lessons**: In Lesson 1 (`P01.M01.L01`), you learned state, behavior, and rich domain models. Today, you protect object state against reference leaks using defensive copying.

# Step 3 — Coding Practice

### Exercise 1: Demonstrating a Reference Leak (Easy)
* **Objective**: Expose a reference leak and watch an external caller break object invariants.
* **Difficulty**: Easy
* **Expected Outcome**:
  1. Create `ReferenceLeakDemo.java` under `scratch/`:
     ```java
     import java.util.Date;

     public class ReferenceLeakDemo {
         static class MutablePeriod {
             private final Date start;
             private final Date end;

             public MutablePeriod(Date start, Date end) {
                 if (start.after(end)) throw new IllegalArgumentException("Start after end!");
                 this.start = start; // REFERENCE LEAK 1!
                 this.end = end;     // REFERENCE LEAK 2!
             }

             public Date getStart() { return start; } // REFERENCE LEAK 3!
             public Date getEnd() { return end; }     // REFERENCE LEAK 4!
         }

         public static void main(String[] args) {
             Date start = new Date();
             Date end = new Date(start.getTime() + 10000);
             MutablePeriod period = new MutablePeriod(start, end);

             // EXPLOIT REFERENCE LEAK: Mutate start date externally to be AFTER end date!
             period.getStart().setTime(end.getTime() + 50000);

             System.out.println("Start is after End? " + period.getStart().after(period.getEnd())); 
             // Output: true (INVARIANT IS BROKEN!)
         }
     }
     ```
  2. Run the code and observe how external code broke the `start.before(end)` invariant without calling any setter!

### Exercise 2: Fixing Reference Leaks via Defensive Copies (Medium)
* **Objective**: Refactor class to make defensive copies in constructors and getters.
* **Difficulty**: Medium
* **Expected Outcome**:
  1. Create `SecurePeriod.java` under `scratch/`:
     ```java
     import java.util.Date;

     public class SecurePeriod {
         private final Date start;
         private final Date end;

         public SecurePeriod(Date start, Date end) {
             // Make defensive copies BEFORE validating invariants!
             this.start = new Date(start.getTime());
             this.end = new Date(end.getTime());
             if (this.start.after(this.end)) {
                 throw new IllegalArgumentException("Start date must be before end date.");
             }
         }

         public Date getStart() { return new Date(start.getTime()); } // Return defensive copy!
         public Date getEnd() { return new Date(end.getTime()); }     // Return defensive copy!
     }
     ```
  2. Write JUnit 5 test `SecurePeriodTest.java` verifying that mutating the returned Date object does NOT break the internal invariant of `SecurePeriod`.
* **Hints**: Make defensive copies BEFORE validating invariants in constructors to prevent time-of-check to time-of-use (TOCTOU) attacks.
* **Common Mistakes**: Validating original parameters before making defensive copies.

# Step 7 — Engineering Insight

### What is a Domain Invariant?
A **Domain Invariant** is a business rule that MUST ALWAYS hold true for an object to be considered valid:
* Example 1: `Account.balance >= 0` (Overdraft Protection).
* Example 2: `Period.start <= Period.end` (Temporal Sanity).
* Example 3: `Order.items.size() > 0` (Non-Empty Cart).

Encapsulation is the architectural enforcement of invariants. If a class exposes raw setters or suffers from reference leaks, external code can bypass validation and leave your domain objects in an illegal, corrupted state.

# Step 8 — Open Source Connection

In JDK **`java.util.Collections.unmodifiableList()` & `java.time.LocalDate`**:
* Modern Java APIs prefer immutable types like `java.time.LocalDate` over mutable `java.util.Date`.
* When wrapping mutable collections, `Collections.unmodifiableList(list)` prevents downstream code from calling `.add()` or `.clear()`, enforcing collection immutability.
