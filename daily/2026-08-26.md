# Step 3 — Coding Practice

### Exercise 1: Ask vs. Tell Anti-Pattern (Easy)
* **Objective**: Identify procedural "Ask" anti-patterns and refactor them into clean "Tell" message passing.
* **Difficulty**: Easy
* **Expected Outcome**:
  1. Create `AskVsTellDemo.java` under `scratch/`:
     ```java
     public class AskVsTellDemo {
         static class Account {
             private double balance = 500.0;
             public double getBalance() { return balance; }
             public void setBalance(double b) { this.balance = b; }
             public void deduct(double amount) {
                 if (amount <= 0 || amount > balance) throw new IllegalArgumentException("Invalid amount");
                 this.balance -= amount;
             }
         }

         public static void main(String[] args) {
             Account acc = new Account();

             // PROCEDURAL "ASK" ANTI-PATTERN: Reaching inside object to calculate!
             if (acc.getBalance() >= 100.0) {
                 acc.setBalance(acc.getBalance() - 100.0);
             }

             // OBJECT-ORIENTED "TELL" MESSAGE PASSING: Sending a command message!
             acc.deduct(100.0);
             System.out.println("Balance after tell: " + acc.getBalance());
         }
     }
     ```
  2. Run the code and note how "Tell" passes the message directly to the target object, allowing the target to protect its own state!

### Exercise 2: Message Passing Collaboration: Notification Dispatcher (Medium)
* **Objective**: Build a message passing collaboration where a service dispatches messages to interface receivers.
* **Difficulty**: Medium
* **Expected Outcome**:

     ```java
     public interface NotificationSender {
         void sendNotification(String recipientId, String message);
     }
     ```

  3. Create `NotificationService.java` holding `List<NotificationSender> senders`. Expose `void broadcast(String recipientId, String message)` which dispatches the message to all registered senders.

* **Hints**: `NotificationService` knows only the `NotificationSender` interface, not concrete implementation classes!
* **Common Mistakes**: Hardcoding concrete classes inside `NotificationService` instead of depending on the interface abstraction.

# Step 7 — Engineering Insight

### Tell-Don't-Ask & Message Passing
Why is **Tell-Don't-Ask** a core object-oriented design principle?

* **Procedural Approach ("Ask")**: Caller queries the target object's state (`getBalance()`), performs calculations externally, and writes the state back (`setBalance()`).
  * *Consequence*: Business logic gets scattered across callers, and invariant checks are easily bypassed.
* **Object-Oriented Approach ("Tell")**: Caller sends a command message (`deduct(100)`). The target object encapsulates both data and behavior, executing the calculation internally while preserving its own invariants.

# Step 8 — Open Source Connection

In JDK **`java.util.concurrent.ExecutorService`**:
* Calling `executor.submit(new TaskRunnable())` is pure Message Passing.
* The caller sends a task message to the executor service. The caller does not know or care which specific worker thread receives or executes the task message, demonstrating complete decoupling of message dispatch from execution.
