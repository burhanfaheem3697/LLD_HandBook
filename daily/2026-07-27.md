# Step 3 — Coding Practice

### Exercise 1: Git Atomic Commits & DAG Inspection (Easy)
* **Objective**: Practice creating atomic commits and inspecting repository commit graphs.
* **Difficulty**: Easy
* **Expected Outcome**:
  1. Create a scratch workspace folder `scratch/git-demo`.
  2. Initialize a Git repository (`git init`).
  3. Create a Java file `VersionedEntity.java`:
     ```java
     public class VersionedEntity {
         private String id;
     }
     ```
  4. Commit: `git add VersionedEntity.java` $\rightarrow$ `git commit -m "feat(core): add VersionedEntity base class"`.
  5. Add a `name` field, commit: `git commit -am "feat(core): add name field to VersionedEntity"`.
  6. Inspect history using `git log --oneline --graph --decorate`. Observe the sequence of commit hashes and the `HEAD -> main` pointer.

### Exercise 2: Branching, Conflict Simulation & Resolution (Medium)
* **Objective**: Create a feature branch, generate a controlled merge conflict, and resolve it manually.
* **Difficulty**: Medium
* **Expected Outcome**:
  1. In `scratch/git-demo`, create and switch to branch `feature/status`: `git checkout -b feature/status`.
  2. Modify `VersionedEntity.java` to add a `private String status = "ACTIVE";` field. Commit it.
  3. Switch back to `main`: `git checkout main`.
  4. Edit `VersionedEntity.java` on the same line to add `private String status = "PENDING";`. Commit it to `main`.
  5. Merge the feature branch: `git merge feature/status`.
  6. Observe the merge conflict warning. Open `VersionedEntity.java`, locate conflict markers (`<<<<<<< HEAD`, `=======`, `>>>>>>> feature/status`), resolve the conflict by keeping `"PENDING_ACTIVE"`, compile with `javac VersionedEntity.java`, and complete the merge commit: `git commit -am "fix(core): resolve status field merge conflict"`.

# Step 7 — Engineering Insight

### Git Commits as Immutable Snapshots
A common misconception is that Git stores line-by-line file diffs. 
* **The Reality**: Git thinks of its data as a series of **snapshots** of a miniature filesystem. Every time you commit, Git takes a picture of what all your files look like at that moment and stores a reference to that snapshot (a Tree object).
* **Immutability**: Every commit hash (SHA-1 or SHA-256) is calculated from the exact content of the files, the parent commit hash, and the author metadata. If a single byte of code changes, the hash changes. This makes Git history cryptographically tamper-proof.
* **Atomic Commits**: Senior engineers make small, focused ("atomic") commits that complete a single logical change. If a commit contains 10 unrelated file edits, debugging regressions using `git bisect` or reverting broken features becomes extremely difficult.

# Step 8 — Open Source Connection

In major open-source Java repositories like **JUnit 5** and **Spring Framework**:
* Every Pull Request must adhere to **Conventional Commits** (e.g. `feat: ...`, `fix: ...`, `docs: ...`, `refactor: ...`).
* Maintainers use `git rebase` and squash merges to ensure that the `main` branch maintains a clean, linear DAG history, making release notes easy to auto-generate.
