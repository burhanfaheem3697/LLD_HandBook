# Step 3 — Coding Practice

### Exercise 1: Identity vs. State Equality (Easy)
* **Objective**: Distinguish between object reference identity (`==`) and state value equality (`.equals()`).
* **Difficulty**: Easy
* **Expected Outcome**:
  1. Create `BankAccountIdentityDemo.java` under `scratch/`:
     ```java
     public class BankAccountIdentityDemo {
         public static void main(String[] args) {
             BankAccount acc1 = new BankAccount("ACC-1001", 500.0);
             BankAccount acc2 = new BankAccount("ACC-1001", 500.0);

             System.out.println("Reference Equality (acc1 == acc2): " + (acc1 == acc2)); // false (different heap memory addresses)
             System.out.println("State Equality (acc1.equals(acc2)): " + acc1.equals(acc2)); // true (same account number and balance)
         }
     }
     ```
  2. Run the file and observe that two distinct object instances with identical field values have different reference identities (`==` is false) but identical state equality (`.equals()` is true).

### Exercise 2: Encapsulating State with Behavior (Medium)
* **Objective**: Build a Rich Domain Model class that encapsulates state behind business behavior methods.
* **Difficulty**: Medium
* **Expected Outcome**:
  1. Create `BankAccount.java` under `scratch/`:
     * Private fields: `private final String accountNumber;`, `private double balance;`
     * Behavior methods: `void deposit(double amount)`, `void withdraw(double amount)`.
     * Preconditions: `deposit` throws `IllegalArgumentException` if `amount <= 0`. `withdraw` throws `IllegalArgumentException` if `amount <= 0` or `amount > balance`.
  2. Write JUnit 5 test `BankAccountTest.java` verifying that depositing $200 increases balance, withdrawing $100 decreases balance, and overdrawing throws `IllegalArgumentException`.
* **Hints**: Do NOT generate setters like `setBalance()`. State mutations must occur through domain methods (`deposit`/`withdraw`).
* **Common Mistakes**: Exposing public setters that allow external code to assign negative balances directly.

# Step 7 — Engineering Insight

### Anemic Domain Model vs. Rich Domain Model
Why do senior architects reject "Anemic Domain Models"?

* **Anemic Domain Model (Anti-Pattern)**:
  A class with private fields and public getters/setters for everything, containing zero business logic. External classes fetch fields, perform math, and set the balance back.
  *Problem*: Invalid state transitions (e.g. negative balances, orphaned records) easily bypass validation!
* **Rich Domain Model (Best Practice)**:
  State is private. Mutations occur exclusively through business behavior methods (`deposit()`, `withdraw()`) that validate invariants before mutating state.
  *Benefit*: The object guarantees its own state validity at all times.
